This inventory keeps the pre-archive survey snapshot, and links for files that have been moved point to the new locations. Archiving of historical versions is now complete. The latest catalog is the historical archive index. Todo descriptions in the inventory are recommendations from before the cleanup.

Core code and evaluation assets need to be kept. Entry points and archive locations for past experiments should be organized. What can be cleaned up directly is mainly caches, system metadata, and empty placeholder files.

This pass only generated the inventory. It did not delete, move, or rename existing files, and it did not commit or push. The inventory records the state before generation. The current code is based on v7, and the next round, v8, is not implemented yet. Historical experiments with negative gains also need to be kept, so they can be reproduced and reported.

Criteria for keeping or not

  • Current E: execution entry points, strategies, data interfaces, scoring, and tests needed to keep developing.
  • Project foundation: needed for the full RAG system, the benchmark, and integrating workstreams. Doing only E does not require loading all of it every time.
  • Review and ground truth: human confirmations, gold, worksheets waiting for review, and their sources. Keep these first.
  • Historical reproduction: old strategies, frozen manifests, input bundles, raw predictions, and logs. Archive them together, and do not recommend them side by side with the current entry points.
  • Regenerable: confirm that the source data or the original archive is intact and has no new manual edits before choosing to clean it up.
  • Cleanable or consolidatable: Python caches, macOS metadata, script shells with no logic, and empty-directory placeholders that are no longer needed.
  • Archive first: locally ignored material that may be the only research record. Do not delete it in one step just because it is ignored.

Suggested way to organize

  1. Tighten navigation first. The README should point only to current progress, current results, current review, and run instructions. Keep old notebooks and reports in the historical navigation so that v1 through v6 are not mistaken for the current entry.
  2. Keep the frozen archive. The original ZIPs, GPU input tar.gz files, per-item predictions, run manifests, and hash indexes are one set of evidence. Do not bulk-delete experiment copies on the grounds of "duplicate content", and do not rewrite a frozen protocol to match a new version.
  3. Clean up only a small scope. Caches and system metadata can be cleaned. scripts/prepare_data.py contains only a TODO; the empty shell can be deleted or a unified entry implemented. docs/.gitkeep and results/.gitkeep no longer serve as placeholders. data/raw/.gitkeep and data/processed/.gitkeep still do.
  4. Align the documentation wording. data/README.md still says that only gitkeep files are committed for the data, but annotations and gold are already present. The progress document places several historical updates side by side, including old wording that "v7 has not been run". Keep the timeline and list the latest status separately. Do not directly rewrite historical wording in a frozen manifest.
  5. Protect material that is not tracked. The local NQ3216 workbook, the Controller integration materials, and some v4 results are ignored. First check whether a trustworthy original archive exists, then decide whether to move or clean them. Do not empty the artifacts directory.
  6. Deal with package placeholders only when integrating other workstreams. Controller and Probe currently have only package entry points. The full code is on other branches. Do not change cross-module interfaces, or merge branches blindly, for the sake of "organizing".
Local disk use and conditions for cleanup

On this machine, data files are about 12.90 GB in logical size, and the filesystem has allocated about 9.68 GB. Most of that is the raw FEVER Wikipedia, downloaded archives, and the processed corpus. They are Git-ignored, which does not mean the remote repository is large. Continuing E development with the frozen C1 does not require loading these large files every time.

  • data/raw/fever/wiki-pages.zip is about 1.71 GB, with unpacked pages about 7.62 GB. After integrity and a way to restore are confirmed, one of the two may be kept.
  • data/processed/retrieval/fever_corpus.jsonl is about 3.52 GB. It can be rebuilt from the raw pages, but full retrieval needs it. Rebuilding after removal costs time.
  • gpu_bundle/ across versions totals about 12.28 MB and consists of unpacked copies, including some cache. Do not add that figure to the cache size and count it twice.
  • The logical size of .venv/ is about 286 MB. It can be reinstalled, but deleting it makes the current local environment unusable. It is not recommended as everyday trash.
  • This machine does not have data/raw/natural_questions/, data/processed/nq_controlled/, or a formal retrieval index. Frozen E inputs can still be used. Rebuilding full NQ retrieval requires the data to be added.

Sizes are measurements from this snapshot, and GB is decimal. Compression, copy-on-write, and sparse files can make logical size differ from space actually used. The multi-gigabyte raw data was not checked byte by byte, so large files get only conditional cleanup advice.
