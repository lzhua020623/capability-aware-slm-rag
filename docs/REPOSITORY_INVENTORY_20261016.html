判断保留与否的标准

  • 当前 E：继续开发要用的执行入口、策略、数据接口、评分和测试。
  • 项目基础：完整 RAG、benchmark 和分工整合要用；仅做 E 不一定每次都加载。
  • 审核与真值：人工确认、gold、待审工作表及其来源，优先保留。
  • 历史复现：旧策略、冻结清单、输入包、原始预测及日志，集中归档，不与当前入口并排推荐。
  • 可再生成：先确认源数据或原压缩包完好、无新人工编辑，再选择清理。
  • 可清理或合并：Python 缓存、macOS 元数据、无逻辑的脚本空壳和已不需要的空目录占位。
  • 先归档：本地被忽略但可能是唯一研究记录的材料，不能按 ignored 一键删除。

建议如何整理

  1. 先收紧导航。README 只指向当前进度、当前结果、当前审核及运行说明；旧版 Notebook 和报告保留在历史导航，避免误把 v1 至 v6 当当前入口。
  2. 保留冻结档案。原始 ZIP、GPU 输入 tar.gz、逐条预测、运行 manifest 和哈希索引是一组证据。不要按“内容重复”批量删实验副本，或改写冻结协议来匹配新版本。
  3. 小范围清理。缓存和系统元数据可清理；scripts/prepare_data.py 只有 TODO，可删空壳或实现统一入口；docs/.gitkeep、results/.gitkeep 已无占位作用。data/raw/.gitkeep 和 data/processed/.gitkeep 仍有作用。
  4. 补齐文档口径。data/README.md 仍说数据只提交 gitkeep，实际已有标注和 gold；进度文档多段历史更新并列，包含旧的“v7 未运行”文字，建议保留时间线并单列最新状态。冻结 manifest 的历史文字不直接改写。
  5. 保护未入库材料。本机 NQ3216 工作簿、Controller 联调及 v4 结果部分被忽略。先验证是否有可信原始归档，再决定移走或清理；不能整目录清空 artifacts。
  6. 整合其他分工时再处理包占位。当前 Controller、Probe 只有包入口；完整代码在其他分支。不要为“整理”改动跨模块接口或盲目合并分支。
本地空间占用与清理条件

本机 data 文件逻辑大小约 12.90 GB，文件系统实际分配约 9.68 GB；主要是 FEVER 原始 Wikipedia、下载压缩包和处理后 corpus。它们被 Git 忽略，不能据此说远端仓库很大。继续用冻结 C1 开发 E 不需要每次加载这些大文件。

  • data/raw/fever/wiki-pages.zip 约 1.71 GB，解压页约 7.62 GB；确认完整性和恢复方式后可择一保留。
  • data/processed/retrieval/fever_corpus.jsonl 约 3.52 GB，可由原始页重建，但完整检索需要它；移除后重建有时间成本。
  • 各版本 gpu_bundle/ 共约 12.28 MB，是解压副本；包括部分缓存，不应和缓存大小相加重复估计。
  • .venv/ 的逻辑大小约 286 MB，可以重装，但删除会让现有本地环境失效；不建议当作日常垃圾。
  • 本机没有 data/raw/natural_questions/、data/processed/nq_controlled/ 和正式检索索引；E 冻结输入可继续使用，完整 NQ 检索重建需补数据。

大小是本快照测量值，GB 为十进制；压缩、写时复制和稀疏文件可能使逻辑大小与实际占用不同。没有对数 GB 原始数据逐字节校验，因此大文件只给条件清理建议。
